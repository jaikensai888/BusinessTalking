# BusinessTalking 研发 Baseline v1

日期：2026-09-08。本文是待执行的验收用例，不代表已经通过，也不代表已经实现自动化。

目标：在保留 Next.js + DSH runtime 架构的前提下，证明人格对话、多人讨论、Skill 调用可以连续使用；发生失败时能定位阶段、保留证据并恢复。

## 1. 范围与判定

- `1v1`：用户与一个人格连续对话；`1vN`：用户发起 N 个人格参与、Moderator 汇总的讨论。N 默认 3，边界测试 N=5。
- P0 为必须通过的发布门槛；P1 为扩展回归，未通过必须列出影响。未来新增要求须单独记入变更，不能暗中修改本 baseline。
- 每项状态只允许 `NOT_RUN / PASS / FAIL / BLOCKED`。缺少凭据、浏览器、故障注入条件、证据或预算时标记 BLOCKED，不能算 PASS。
- “有文字”不等于成功。正常回合须有真实非空 assistant 消息、正常结束事件、已提交的回合与消息关联，以及一致的 UI 状态。失败用例以正确失败和保留诊断信息作为通过标准。
- 模型内容采用事实约束和结构检查，不做整段文本精确匹配。Skill 是否调用以工具事件为准，不采信模型自称“已调用”。
- `23SW5T` 仅作为历史线索；新建测试讨论复现，不编辑、删除或继续运行该历史讨论。缺少 step/start 只能缩小失败阶段，不能直接确定具体 hook 根因。

## 2. 测试层与环境

| 层 | 验证内容 | 限制 |
| --- | --- | --- |
| A：确定性自动化 | 编排、隔离、事件投影、审批、错误传播、故障注入 | 可 mock 模型；不能替代真实链路 |
| B：真实集成 | 实际 Node runner、DSH、模型、数据库、Skill | 必须记录实际 provider/model/DSH 版本 |
| C：浏览器验收 | 发送、流式过程、刷新、审批、最终回复 | 必须操作真实页面；API 成功不能代替 UI 通过 |

准备要求：

1. 记录 commit、未提交 diff 摘要、Node/pnpm/DSH 版本、provider/model、脱敏后的配置指纹、平台、测试时间。固定这些变量后再比较前后结果。
2. 优先使用隔离测试数据库、DSH home 和独立端口；先检查实际数据库 URL 解析方式及配置读取逻辑，确认不会连接用户数据。不能确认隔离时停止相关写操作，不直接运行 reset/seed/migrate dev。
3. 启动方式沿用真实 Node 下的 `pnpm dev`；项目默认端口 3001，使用前确认占用进程归属。不得终止其他任务服务。
4. 每批生成唯一 `baseline-<时间>-<随机串>` 标识，关联 fixture、discussionId、sessionId 和产物。只清理明确归属该批的资源；失败证据先保存。
5. 凭据使用既有安全配置；不得把 API Key、审批 token、完整环境变量或用户私有内容写入报告。真实模型与搜索会产生外部请求。
6. 执行默认上限：每次 loop 最多 5 次修复迭代、60 分钟、100 次真实模型请求，任一先到即停。请求次数包含 Persona、Moderator、工具续步和重试；无法计量时先补计量或阻塞真实测试，不能用讨论次数代替。该上限是执行保护，不是价格承诺。
7. 单个模型回合默认验收等待上限 120 秒；人工审批等待单独计时，最多 180 秒。超时保留证据并结束本项，不通过无限延时掩盖问题。这些是测试预算，不要求直接改生产超时配置。

## 3. 固定测试素材

通过隔离 fixture 创建人格，沿用现有导入/持久化契约；不要假设生产库里存在指定 ID。

| 素材 | 内容与用途 |
| --- | --- |
| Persona A：需求验证员 | 关注付费人群、访谈和证据；中文简短回答；明确区分已知与假设 |
| Persona B：成本审查员 | 关注成本、毛利和履约；中文简短回答 |
| Persona C：反方评审员 | 关注反例、失败条件和退出标准；中文简短回答 |
| Persona D/E | 用于并发边界，分别关注交付与获客 |
| 讨论题目 | “面向独立咖啡店提供每月 299 元的短视频选题服务，先验证需求。不要联网，每次不超过 150 字。” |
| 连续对话第 1 问 | “项目代号是 BT-ORANGE-17，预算 3000 元，目标客户是独立咖啡店。请给一个需求验证动作，不要联网。” |
| 连续对话第 2 问 | “沿用刚才的项目，请复述项目代号、预算和客户，再给一个不同的验证动作。”（不重复事实，检验历史恢复） |
| 第 3 问 | “预算改为 1800 元，其他条件不变。复述最新预算和项目代号，说明先做哪一步。” |
| 第 4/5 问 | 分别询问“当前预算与客户是什么？”和“结合之前的动作，给出三步执行顺序。” |

普通 Skill fixture `baseline-checklist`：最小合法 SKILL.md 定义名称与描述，正文要求按“已知事实、待验证假设、下一步实验”三项输出；在正文放入每批随机生成的 skillMarker。`references/check.txt` 放入不同随机 referenceMarker 和验收句“先访谈 3 家店，再决定是否开发”。两个 marker 均不放入用户输入、人格提示词或讨论 brief。

安装为不可变 Skill revision，记录 revisionId、内容 hash、marker 的证据文件路径。Skill 测试输入：“请调用 baseline-checklist 技能，并用 read_skill_reference 读取其 references/check.txt；引用其中的验收句及校验标记，然后按该技能结构分析当前项目。”工具参数遵循实际 schema，不自行假设。至少要有对应的 skill 与 read_skill_reference 调用、结果和同一 Session 的关联证据；若标记已被系统预加载，仅凭输出标记不能证明发生了调用。

以下按功能组织用例，优先级在表格内标注。所有用例共同收集第 7 节证据；测试层 A/B/C 的含义见第 2 节。故障注入仅在隔离环境或测试替身执行。

## 4. 单人讨论（1v1）

验证一个人格的连续对话、上下文恢复、技能调用与重复提交。

| ID | 测试功能 | 优先级 | 测试层 | 操作步骤 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| B01 | 首次提问 | P0 | B+C | 创建 A 的 1v1，发送第 1 问，等待结束后刷新 | 一条真实最终回复；UI 可见；落库一次；回合 completed，页面可继续输入 |
| B02 | 同一会话第二次提问 | P0 | B+C | 在 B01 原讨论发送第 2 问 | 原人格 sessionId 不变；准确保留三个事实；本次有正常事件和独立消息；不是新 Session 冒充复用 |
| B03 | 连续五次对话与信息更新 | P0 | B+C | 原讨论依次发送第 3～5 问，每次等结束 | 五次回复均成功；后续预算为 1800；无重复消息、卡住或丢失前文 |
| B04 | 关闭页面后续聊 | P0 | B+C | 完成第 1 问后关闭页面、重新进入讨论，再发送第 2 问 | 历史完整、sessionId 稳定、事实保留，新回复正常显示 |
| B05 | 重启服务后续聊 | P0 | B+C | 完成第 1 问后仅重启本批应用/runner，再发第 2 问 | 历史恢复正确、逻辑 sessionId 不变、不重复插入旧消息，第二问正常完成 |
| B06 | 两个单人讨论隔离 | P0 | A+B | 同时创建两个 A 的讨论，各写不同代号；随后各自询问代号 | 两讨论 Session 不同；回复与事件均无串线；不会互相覆盖状态 |
| S01 | 首次 Skill 调用 | P0 | B+C | 1v1 勾选 fixture revision，发送 Skill 测试输入 | 真实 skill 与 read_skill_reference 调用成功；revision/路径正确；标记与结构正确；工具过程 UI 可见；最终消息落库 |
| S02 | 同一会话再次调用 Skill | P0 | B+C | S01 原 Session 再次要求调用同一技能并读取 reference | 第二次也有真实调用与结果，无 scoped provider 恢复错误；Session 稳定 |
| X02 | 运行中重复提交 | P1 | A+C | 同一 Session 运行中再次提交（包含双击） | 后端拒绝冲突或按明确契约处理；不同时运行两次、不重复回复，前端有明确反馈 |

## 5. 多人讨论（1vN）

验证多个人格的发言、跨轮上下文、主持人汇总、技能与审批共享，以及局部失败恢复。

| ID | 测试功能 | 优先级 | 测试层 | 操作步骤 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| B07 | 三人单轮讨论 | P0 | B+C | A/B/C，rounds=1，使用固定题目 | 三个人格各有真实发言和独立稳定 Session；Moderator 在本轮人格全部结束后汇总；成功输出不重复，UI 归属正确 |
| B08 | 三人多轮讨论 | P0 | A+B+C | A/B/C，rounds=2 | 各人格完成两轮，Moderator 完成两轮（默认正常共 8 个回合）；各自 Session 跨轮稳定；第二轮取得第一轮已提交内容；Moderator 只汇总真实成功发言 |
| B09 | 两个多人讨论隔离 | P0 | A+B | 两个不同讨论分别发起三人讨论 | discussionId、runId、Session、事件和状态隔离；一个结束/失败不改另一个 |
| S03 | 多人分别调用 Skill | P0 | B+C | 三人一轮勾选 fixture，明确要求每个人格调用 | 每个人格均有可归属的真实 Skill 调用/结果；不能由一个人的事件代替全部；Moderator 能正常汇总 |
| A01 | 搜索批准与讨论级授权 | P0 | A+B+C | 在支持搜索的人格配置中发起搜索，批准；同讨论其他人格再搜索 | 批准前工具没有执行；批准后有真实执行结果；web_search 的讨论级授权不重复弹窗，另一讨论不继承授权 |
| A02 | 搜索拒绝与讨论级拒绝 | P0 | A+B+C | 新讨论搜索请求选择拒绝，再让另一人格尝试 | 拒绝后无搜索执行；同讨论后续请求不重复询问；拒绝记录可查；UI 解除等待。若 DSH 将拒绝结束为失败，须明确显示且可继续操作 |
| F01 | 单个人格失败 | P0 | A | 三人一轮，仅给其中一人注入 DSH_TURN_FAILED | 其余继续；失败人格可见，Moderator 仅使用成功消息；不得伪造失败人格发言 |
| F02 | 全员失败与主持人异常 | P0 | A | 本轮全部人格失败；另测 Moderator 返回无效 JSON | 全员失败不启动汇总；Moderator 非法输出不更新成功状态或伪造共识；两种错误均可追踪 |
| X01 | 五人并发与排队 | P1 | A+B | 5 人一轮，并发上限配置为 4 | 活跃 Persona 不超过 4；排队者最终执行；有时间区间/计数证据；Moderator 串行在后 |
| X03 | 讨论中插话 | P1 | A+B | 多人讨论中插话“预算变为 1800” | 插话在约定的下一轮快照被消费一次；不写入已经启动的同轮快照，不丢失或重复 |
| X04 | 失败人格重试 | P1 | A+B | 失败 Persona 使用原 Session 显式重试 | attempt 增加；保留失败记录，成功结果只提交一次；其他人格不被重新执行 |
| X05 | 归档与恢复讨论 | P1 | A+B | 运行中归档本批讨论，之后恢复并继续 | 旧 run 不再提交结果；恢复历史完整，按已提交轮次续跑；不误改其他讨论 |

## 6. 通用能力

集中列出单人和多人讨论共用的权限、事件、错误诊断与 Skill 版本契约；每次执行须记录实际讨论模式。

| ID | 测试功能 | 优先级 | 测试层 | 操作步骤 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| S04 | 未授权 Skill 访问 | P0 | A+B | 新讨论不勾选 fixture；提示尝试读取该技能；A 层直接测试越权调用 | 未授权 revision 内容不会泄漏；实际 guard 拒绝越权调用；B 层若模型未发起调用，只能证明未泄漏，不能单独证明 guard 生效 |
| O01 | 流式断线与事件重放 | P0 | A+B+C | 在生成中刷新/断开浏览器事件流，再重连 | 已提交事件重放后无缺失、无重复最终消息；不触发第二次模型回合；最终 UI 与数据库一致 |
| O02 | 模型调用前异常诊断 | P0 | A+B | 注入模型调用前的可识别异常（唯一 errorMarker），执行一个回合 | 明确失败；保留原始 code/message，存在的 stack、agent/error 和 stderr 经脱敏保留；不会只报“空回复”；失败前已收事件可追溯 |

| O04 | 无有效回复与错误结束 | P0 | A | 注入正常结束但无 assistant 内容、以及错误结束两种情况 | 前者明确“缺少有效回复”；后者保留真实错误；两者都不得写成功或伪造 assistant 回复 |
| X06 | Skill 版本冻结 | P1 | A+B | fixture 安装新 revision，旧讨论继续，新讨论选新版 | 旧讨论仍使用冻结 revision，新讨论用新版；以 revision/hash/工具结果验证 |
| X07 | 凭据、超时与协议错误 | P1 | A | 注入错误凭据、超时、错误 Session 事件、损坏 runner frame | 分别产生可区分错误或明确协议错误；无伪成功、无跨会话入库、无泄露凭据 |

## 7. 每项证据与结果记录

产物放在 `docs/testing/runs/<batchId>/`，每次新建，不能覆盖历史结果。每项记录：

- ID、层、状态、开始/结束时间、步骤、输入、期望与实际、使用的脚本/命令/浏览器操作。
- discussionId/shortId、participantId、sessionId、runId、turnId、attempt；未产生的字段填“不适用”及原因，不能编造。
- 原始事件（脱敏 JSONL）及 seq、时间、调用关联 ID；数据库回合/消息/事件快照；UI 项保存过程与完成截图。
- 失败保留 turn/end.reason 全部可用错误信息、agent/error、runner stderr、exitCode/signal、最后事件及已确认阶段。上游未提供 stack 时明确写 unavailable，不编造。
- 真实模型请求计数、耗时；token/成本只在有可靠数据时记录，否则写 unavailable。
- 根因分为“已证实 / 假设 / 未知”；列复现命令、修复 diff、回归证据与遗留问题。

建议汇总表：`ID | 层 | 状态 | 证据相对路径 | 缺口/失败摘要 | 下一步`。同一 ID 不同层分别列行；只有所有要求层通过才将该 ID 汇总为 PASS。

完成标准：所有 P0 在同一最终代码与固定环境配置下通过；最终版本 B02（原会话第二问）、B05（重启续聊）、S02（第二次技能调用）各在三个独立新讨论中连续通过，失败即重新累计，保留之前失败记录。P1 全部执行或明确记录 BLOCKED/FAIL 与影响。预算不足时保存进度，不能降低门槛宣布完成。内容质量问题和执行链路问题分别归因，但都不能默认为通过。

已有命令（PowerShell，项目根目录）：

```powershell
pnpm test
pnpm lint
pnpm build
```

`pnpm test` 默认不执行 RUN_DSH_E2E 门控的真实模型 smoke。准备好隔离环境与计量后，可显式执行已有 smoke：

```powershell
$env:RUN_DSH_E2E = '1'
pnpm exec vitest run tests/e2e/dsh-session-observability.test.ts --testTimeout=120000
Remove-Item Env:RUN_DSH_E2E
```

若原环境已有 RUN_DSH_E2E 值，执行器应保存并恢复原值。以上只运行已有 smoke，不是完整 baseline 命令。后续 loop 需补齐自动化与 fixture，记录新增命令；不要引用尚不存在的 `test:baseline`。
